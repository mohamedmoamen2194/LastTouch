# 1. Project Overview

## 1.1 Introduction

LastTouch is an AI-powered Business Operating System (Business OS) built for beauty and grooming businesses.

Unlike simple booking systems, LastTouch manages every aspect of operating a modern beauty business including:

- Online Booking
- Customer CRM
- Employee Management
- Scheduling
- Services
- Analytics
- Business Insights
- AI Receptionist
- Marketing Automation
- Subscription Management
- Multi-location support (future)
- Marketplace (future)

The platform is designed as a multi-tenant SaaS application where thousands of independent businesses operate securely within a shared infrastructure while maintaining complete data isolation.

The first supported business types are:

- Men's Barber Shops
- Women's Hair Salons

The architecture must be generic enough to support additional business types without major code changes.

Examples include:

- Beauty Centers
- Nail Studios
- Makeup Artists
- Spas
- Massage Centers
- Clinics
- Wellness Centers

The backend must never be tightly coupled to any specific business type.

---

# 2. Vision

Our vision is to become the operating system for appointment-based businesses in the Middle East.

Instead of being known as a booking application, LastTouch should become the daily workspace where business owners manage their entire business.

Booking is only one feature.

The platform should help owners:

- Save time
- Increase revenue
- Reduce missed appointments
- Improve customer retention
- Understand their business through analytics
- Automate repetitive work using AI

# 3. Product Philosophy

The platform follows six core principles.

## Principle 1

### Self-Service First

Every tenant manages their own business.

Platform administrators should never edit:

- Services
- Employees
- Prices
- Working hours
- Branding
- Gallery
- Business information
- Promotions

Everything must be configurable by the tenant.

The platform only manages infrastructure.

---

## Principle 2

### Configuration Over Customization

The application should be driven by configuration.

Business Type determines:

- terminology
- colors
- homepage
- default services
- employee naming
- AI prompts
- icons

No duplicate applications should exist.

There is only one application.

Everything changes through configuration.

---

## Principle 3

### Multi-Tenant By Default

Every feature must support multiple tenants.

Every database query must always be scoped by:

tenant_id

No exception.

---

## Principle 4

### AI Native

Not an afterthought.

Every module should be designed with future AI integrations in mind.

↓

## Principle 5

### Mobile First

Most business owners will use LastTouch from mobile devices.

No desktop-only workflows.

## Principle 6

# 7. Engineering Principles

The following engineering rules are mandatory.

## TypeScript

Strict mode enabled.

Avoid `any`.

Prefer inferred types.

Use interfaces only when extension is required.

Prefer type aliases elsewhere.

---

## Components

Components should remain small.

Business logic belongs outside UI components.

UI components should not perform database operations.

---

## Validation

Every input must be validated using Zod.

Validation must occur:

- client side
- server side

Never trust client input.

---

## Error Handling

Never expose internal errors.

Return standardized error responses.

Every mutation should return:

- success
- message
- optional payload

---

## Database

Use UUIDs.

Use timestamps.

Use foreign keys.

Soft delete where appropriate.

Never permanently delete business-critical records.

---

## Security

Never trust client permissions.

Every API route must verify:

- authenticated user
- tenant membership
- role
- subscription
- feature access

on the server.

---

## Performance

Prefer Server Components.

Use Client Components only when interactivity requires them.

Avoid unnecessary hydration.

Optimize images.

Lazy load heavy modules.

---

## Code Quality

Follow SOLID principles.

Favor composition over inheritance.

Avoid duplicated logic.

Extract reusable utilities.

Build for long-term maintainability rather than short-term speed.

# 8. System Architecture

LastTouch is a **multi-tenant SaaS platform** built using a modular, domain-driven architecture.

The application consists of a single codebase serving multiple independent businesses (tenants).

Each tenant has complete data isolation while sharing the same infrastructure.

The platform should be horizontally scalable without requiring architectural changes.

The application consists of three logical layers:

```text
Presentation Layer
│
├── Public Booking Website
├── Business Dashboard
├── Employee Dashboard
└── Platform Dashboard

↓

Application Layer

├── Authentication
├── Authorization
├── Booking Engine
├── CRM
├── Employees
├── Customers
├── Notifications
├── AI
├── Billing
├── Analytics

↓

Infrastructure Layer

├── PostgreSQL (Neon)
├── Drizzle ORM
├── Clerk
├── Cloudflare R2
├── Resend
├── Paymob
├── Vercel
```

Each domain must be isolated.

Avoid coupling unrelated modules together.

Example:

The Booking module must never directly manipulate Billing.

Instead, communication should occur through service methods.

# 10. Multi-Tenant Architecture

Multi-tenancy is the foundation of LastTouch.

Every business is a Tenant.

Examples:

- Fade Zone
- Kings Barber
- Luxury Salon
- Golden Touch

Internally:

```
Tenant

↓

Employees

↓

Customers

↓

Appointments

↓

Services

↓

Reports
```

Every tenant owns:

- employees
- customers
- appointments
- services
- gallery
- branding
- settings
- analytics
- AI configuration

No tenant can access another tenant's data.

Tenant isolation is mandatory.

---

## Tenant Identification

Each tenant has:

- UUID
- Slug
- Display Name

Example

```
lasttouch.app/fade-zone

lasttouch.app/luxury-salon
```

Future support:

```
fadezone.com
```

or

```
book.fadezone.com
```

The architecture must support custom domains without major refactoring.

---

## Tenant Resolution

Every request must resolve the tenant before any business logic executes.

Resolution order:

1. Custom Domain
2. Subdomain (future)
3. URL Slug
4. Tenant Context

If a tenant cannot be resolved:

Return 404.

Never fallback to another tenant.

---

## Tenant Context

Every authenticated request must have access to:

- tenantId
- userId
- membership
- role
- subscription
- enabledFeatures
- businessType

This context should be created once and reused throughout the request lifecycle.

# 16. Database Design

The database is designed around a multi-tenant architecture.

Every business operates independently while sharing the same PostgreSQL database.

Business-specific data must always be scoped using `tenant_id`.

The schema must be normalized, indexed, and designed for long-term scalability.

---

## Database Rules

The following rules apply to every table unless otherwise specified.

Every table must contain:

- id (UUID Primary Key)
- created_at
- updated_at

Business-related tables additionally contain:

- tenant_id

Never use auto-increment integers.

Always use UUIDs.

---

## Timestamp Rules

created_at

Automatically populated.

Never modified.

updated_at

Automatically updated on every modification.

---

## Soft Deletes

Business-critical data must never be permanently deleted.

Instead use

deleted_at

Examples:

Customers

Employees

Services

Appointments

Business Settings

Historical records must remain intact.

---

# 18. Appointment Engine

The appointment engine is the heart of LastTouch.

Every booking must pass through the scheduling engine.

The scheduling engine is responsible for determining:

- availability
- conflicts
- buffers
- employee schedule
- breaks
- vacations
- business hours
- booking rules

No appointment may bypass this validation.

---

# Appointment Lifecycle

Appointment

↓

Pending

↓

Confirmed

↓

Completed

or

Cancelled

or

No Show

---

Status definitions

Pending

Created but awaiting confirmation.

Confirmed

Accepted by the business.

Completed

Finished successfully.

Cancelled

Cancelled by customer or business.

No Show

Customer did not arrive.

---

# Scheduling Rules

Before creating an appointment the engine must validate:

✓ Business is open

✓ Employee is working

✓ Employee is not on leave

✓ Requested slot is not inside a break

✓ Appointment does not overlap another

✓ Minimum notice is respected

✓ Maximum booking window is respected

✓ Feature is enabled

If any validation fails

Return validation error.

Never automatically adjust appointments.

# 28. Artificial Intelligence Architecture

Artificial Intelligence is a first-class module within LastTouch.

AI should never exist as a standalone chatbot.

Instead, AI capabilities are distributed throughout the platform to assist business owners, employees, and customers.

Every AI capability must use the same AI infrastructure while exposing different specialized assistants.

The AI layer must be modular so that models, prompts, tools, and providers can evolve independently.

---

# AI Philosophy

The AI should function as another member of the business.

Examples:

• Receptionist

• Marketing Assistant

• CRM Assistant

• Analytics Assistant

• Business Consultant

Every assistant has a different responsibility while sharing the same business knowledge.

# 45. Coding Standards

Never place business logic inside React components.

Never access Drizzle directly from UI components.

Every mutation passes through an Application Service.

Repositories only communicate with the database.

Business rules belong to Domain Services.

Server Actions should call Application Services.

Never duplicate validation.

Prefer composition over inheritance.

Avoid global state whenever possible.

Keep components small and reusable.

Prefer Server Components.

Client Components should only exist when interactivity is required.

Always infer TypeScript types from Zod schemas.

Every module should expose a public API.

Avoid importing deep internal files from another module.

Prefer dependency injection over singleton patterns.

Never create helper files with unrelated utilities.

Keep utility functions close to the domain that owns them.
